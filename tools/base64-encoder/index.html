About Base64 encoding

      
Base64 turns arbitrary bytes into a string using only 64 printable ASCII characters (A–Z, a–z, 0–9, +, /, with = as padding). It's commonly used to embed binary-ish data — images, tokens, credentials — inside text formats like JSON, URLs, or HTTP headers that can't safely carry raw bytes. Every 3 bytes of input become 4 Base64 characters, which is why encoded output is consistently about a third larger than the original — there's no compression happening, only a change of alphabet.

      
Why UTF-8 handling matters

      
A bare call to the browser's built-in btoa() function throws on any character outside the Latin-1 range — accented letters, emoji, CJK text all break it, because btoa expects a "binary string" where every character is a single byte. This tool encodes the UTF-8 byte sequence instead, so café ☕ round-trips correctly instead of throwing InvalidCharacterError partway through.

      
Worked example

      
Encoding the text hello produces aGVsbG8= — five bytes of input becoming eight Base64 characters plus one padding character, since 5 isn't evenly divisible by 3. Try encoding a single character at a time and you'll see the padding shift: one input byte needs two =, two input bytes need one, and three or more input bytes need none until the next group starts.

      
Base64 vs. Base64url

      
Standard Base64's + and / characters both have special meaning inside a URL, so a Base64 string containing them isn't safe to drop directly into a query parameter without also URL-encoding it — a common source of mangled tokens. A variant called Base64url (used by JWTs, among other things) swaps in - and _ and usually drops the = padding entirely so the result is URL-safe on its own; this tool produces standard Base64, so if the output is headed into a URL, either run it through the URL Encoder first or use a Base64url-aware library at the point where it's actually needed.
