URL Encoder

Percent-encode a string so it's safe inside a URL. Use "Encode component" for a single query value, or "Encode full URI" to leave reserved characters like / and ? untouched.

Component vs. full-URI encoding

      
Encode component (encodeURIComponent) escapes everything that isn't safe in a single query parameter or path segment — including /, ?, & and =. Use it when encoding one value that will be inserted into a URL, since those reserved characters need escaping precisely because they'd otherwise be mistaken for URL structure rather than part of your data.

      
Encode full URI (encodeURI) assumes the input is already a complete URL and leaves reserved characters like :, /, ? and & alone, only escaping spaces and other genuinely unsafe characters. Running a whole URL through encodeURIComponent instead is a very common mistake — it also escapes the : and / that make the string a URL in the first place, turning https://example.com/a b into an unusable mess like https%3A%2F%2Fexample.com%2Fa%20b, rather than the correct https://example.com/a%20b.

      
Worked example: query string values

      
Say you're building ?q=<value> and the value is C++ & Java. Use Encode component on just that value — the result, C%2B%2B%20%26%20Java, is safe to append after q=. If you instead ran the entire URL (https://example.com/search?q=C++ & Java) through Encode full URI, the & and = that make up the query string's own structure would be left untouched (correct), but so would the literal & inside your value — which a server would then misread as the start of a second query parameter. That's the core rule: encode the whole URL with encodeURI, but encode each individual value with encodeURIComponent before slotting it in.

      
The double-encoding trap

      
Running an already-encoded string through the encoder again turns every % into %25, producing something like %2520 instead of %20 — decoding it once gets you back to %20, not a space. If your output looks like it has an extra %25 where a percent sign should be, the input was likely encoded twice; decode it twice (or check further upstream for where the double-encoding is happening) rather than encoding it a third time.
