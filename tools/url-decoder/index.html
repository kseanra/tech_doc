Why decoding sometimes fails

      
Percent-encoding represents one byte as % followed by exactly two hex digits — %20 for a space, %2F for a forward slash, and so on. Decoding throws an error when a % isn't followed by two valid hex characters, which usually means one of three things: the string was already decoded once and the remaining % is a literal percent sign that was never meant to be decoded again; the string was truncated mid-sequence when it was copied (a common casualty of character limits in chat apps and spreadsheets); or it isn't actually percent-encoded at all and just happens to contain a %.

      
Worked example

      
hello%20world decodes to hello world. Try decoding 100% off the same input box and you'll get the "not valid percent-encoding" error, because % here is a literal percent sign with nothing valid following it — exactly the ambiguity that makes this error common on any text that legitimately contains a % character alongside real encoded segments.

      
+ in query strings

      
Inside a URL's query string specifically (not the path), a literal + traditionally means a space — a convention from HTML form submission (application/x-www-form-urlencoded), not from the URL spec itself. This tool's decoder follows decodeURIComponent's behavior, which treats + literally and does not convert it to a space; if you're decoding a query string that came from an HTML form and expect + to mean space, you'll need to swap + for %20 (or a literal space) before decoding, or use a form-data-aware parser instead.
