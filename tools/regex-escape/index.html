Why you need to escape a string before it goes in a regex

      
A regular expression treats a set of characters as instructions rather than literal text: . means "any character," ( and ) mark a capture group, * and + are quantifiers, ^ and $ anchor to the start and end of a line, and [, ], {, }, |, and \ all carry their own special meaning. If you build a pattern by concatenating a raw string into it — a filename typed by a user, a hostname pulled from a config file, a search term someone entered into a search box — any of those characters can silently change what the pattern matches, or throw a "nothing to repeat" or "unterminated character class" error at runtime.

      
This tool runs the same escaping logic JavaScript's own documentation recommends: every character in the set . * + ? ^ $ { } ( ) | [ ] \ gets a backslash in front of it, turning the string into a sequence that a regex engine will match character-for-character instead of interpreting.

      
A concrete example

      
Say you want to find every occurrence of the literal filename report (final).pdf inside a block of text using a regex. Used unescaped, (final) would be read as a capture group and the parentheses would vanish from the match entirely — the search would actually be looking for report final.pdf with no parentheses at all, which is not what you typed. Run it through this tool first and you get report\ \(final\)\.pdf, which matches the string byte-for-byte, including the parentheses and the literal dot before pdf.

      
The forward-slash option

      
Escaping / is not part of the standard character set, because / has no meaning inside a regex pattern itself — it only matters if you're pasting the result inside a JavaScript regex literal written as /pattern/flags, where an unescaped / would prematurely end the literal. Tick the checkbox above if that's how you plan to use the output; leave it unticked if you're passing the escaped string to new RegExp(...) as a plain string, where / needs no special treatment.
