Docker CLI

Essential Docker commands and quick examples to get containers running locally.

grep -i
docker-basics.sh cli 
# show Docker version
docker --version

# test installation (runs a tiny container that prints a message)
docker run hello-world

# pull an image from Docker Hub
docker pull nginx:latest

# list images on the local machine
docker images

# list running containers
docker ps

# list all containers (including stopped)
docker ps -a

# run a container in the background, map port 80
docker run -d -p 8080:80 --name web nginx:latest

# run an interactive shell in a new container and remove when exited
docker run --rm -it alpine sh

# run a command in a running container (get a shell)
docker exec -it web /bin/bash

# view live logs for a container
docker logs -f web

# stop / start a container
docker stop web

docker start web

# remove a stopped container
docker rm web

# remove an image
docker rmi nginx:latest

# build an image from a Dockerfile in the current dir
docker build -t myapp:latest .

# helpful cleanup: remove dangling images
docker image prune -f

Essential Docker CLI commands to get containers running, inspect images/containers, and perform cleanup.

docker-volumes.sh cli 
# bind mount: sync a host folder straight into the container
docker run -v $(pwd)/data:/app/data myapp

# named volume: storage Docker manages for you, independent of any container
docker volume create mydata
docker run -v mydata:/app/data myapp

# list, inspect, and remove volumes
docker volume ls
docker volume inspect mydata
docker volume rm mydata

Anything a container writes to its own filesystem lives in a writable layer that's destroyed the moment you docker rm it — a very common "why did my database lose all its data" surprise. A bind mount ties a path directly to something on the host; a named volume is storage Docker manages on your behalf. Either one survives container removal, which is what you actually want for anything worth keeping.

docker-compose-basics.yml cli 
# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      - redis
  redis:
    image: redis:7

# start everything defined above, rebuilding images if needed
docker compose up --build

# stop and remove containers + network (not volumes, by default)
docker compose down

Compose turns a pile of docker run flags into one readable file, and every service in it can reach the others by name — web connects to redis:6379 with no manual --network setup, because Compose puts all its services on a shared network automatically. That's the same service-name addressing that fixes the classic Redis "connection refused" error when an app and Redis end up in separate containers.

docker-cleanup.sh cli 
# see how much space images, containers, and volumes are using
docker system df

# remove stopped containers, unused networks, dangling images, build cache
docker system prune

# also remove ALL unused images (not just dangling ones) and unused volumes
docker system prune -a --volumes

"Dangling" means an image layer with no tag at all, usually left behind by a rebuild — plain prune only touches those, so it's safe to run often. -a removes every image not used by a running container, tagged or not, and --volumes also deletes unused named volumes — run that combination deliberately, since it's the one that can actually delete data you meant to keep.
