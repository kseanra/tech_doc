AWS: S3 Access Denied (403 Forbidden)

Four separate permission layers can each independently block an S3 request — here's how to find out which one actually is.

The error

A request to read, write, or list an S3 object or bucket fails with:

<Error>
  <Code>AccessDenied</Code>
  <Message>Access Denied</Message>
</Error>

(HTTP 403.) Notably, S3 gives you almost no detail about which rule denied the request — by design, to avoid leaking information about a bucket's configuration to an unauthorized caller.

Why it happens

S3 access is the intersection of up to four independent policy layers, and if any one of them denies the request, the whole request is denied — there's no "majority rules." The layers, roughly in the order worth checking:

  • IAM policy — attached to the user or role making the request. Does it grant s3:GetObject (or whichever action) on this specific bucket/key path?
  • Bucket policy — attached to the bucket itself, can grant or explicitly deny access regardless of IAM. An explicit "Effect": "Deny" here always wins over any IAM allow.
  • S3 Block Public Access settings — account-level and bucket-level switches that can override even a bucket policy that otherwise grants public access, specifically to prevent accidental public exposure.
  • Object ACLs — legacy per-object permissions, largely superseded by bucket policies but still checked if present, especially on objects uploaded by a different AWS account.

Fix it

Start with AWS's own diagnostic tool rather than guessing — IAM Access Analyzer's policy simulator (or the newer console "Check public access" panel on the bucket) can evaluate a specific principal against a specific action and object, and tells you which layer is actually responsible for the denial:

aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:role/my-role \
  --action-names s3:GetObject \
  --resource-arns arn:aws:s3:::my-bucket/my-key

If that's not available, check in this order: confirm the IAM policy grants the action on the exact resource ARN (a wildcard-free typo in the bucket or key path is a very common cause); check the bucket policy for an explicit Deny statement, which silently beats any Allow elsewhere; and if the request is meant to be public or cross-account, confirm Block Public Access isn't set at the account or bucket level, since it overrides bucket-policy grants specifically to stop accidental exposure.

Cross-account access specifically

When the caller is in a different AWS account than the bucket owner, both the calling account's IAM policy and the bucket owner's bucket policy must explicitly allow the action — one side granting access is never sufficient on its own. This is the most common cause of "it works for me but not for our other account" reports.
