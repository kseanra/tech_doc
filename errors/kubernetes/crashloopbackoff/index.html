Kubernetes: CrashLoopBackOff

A status, not a cause — the container is starting, crashing, and being restarted on an increasing backoff delay. Here's where to actually find out why.

The error

kubectl get pods shows a pod stuck like this:

NAME                     READY   STATUS             RESTARTS   AGE
my-app-7d8f9c6b4-x2kqz   0/1     CrashLoopBackOff   7          6m

Why it happens

CrashLoopBackOff just means Kubernetes tried to start the container, the container process exited (crashed, or exited cleanly with a non-zero code), and Kubernetes is now waiting progressively longer between restart attempts (the "backoff") to avoid hammering a container that's never going to succeed. It's a symptom, not a diagnosis — the actual cause is almost always in the application's own logs from the crashed attempt, not in anything Kubernetes itself reports directly.

Fix it — find the real error first

The single most useful command here is checking the logs from the previous (crashed) attempt, not the current one, since a fast-crashing container may not have current logs yet:

kubectl logs my-app-7d8f9c6b4-x2kqz --previous

This almost always shows the application's own stack trace or startup error — a missing environment variable, a database connection failure, an unhandled exception during startup. Fix whatever that log actually says first; the CrashLoopBackOff status itself gives you no information about the cause beyond "the container isn't staying up."

If --previous shows nothing useful, get the full picture of what Kubernetes thinks happened, including resource limits and events:

kubectl describe pod my-app-7d8f9c6b4-x2kqz

Look specifically at the Last State and Events sections near the bottom — a container killed for exceeding its memory limit shows OOMKilled here, which application logs alone won't always make obvious.

Common root causes once you can see the real error

  • Missing configuration — a required environment variable, ConfigMap, or Secret the container expects isn't mounted or set.
  • Failing readiness/liveness probe combined with a startup that's simply slower than the probe's initial delay — the app is fine, but Kubernetes keeps killing it before it finishes booting.
  • OOMKilled — the container's memory limit is set lower than what it actually needs; check resources.limits.memory in the pod spec.
  • Wrong command or entrypoint — the image's CMD/ENTRYPOINT exits immediately because it was built for a different invocation than the one the pod spec provides.
