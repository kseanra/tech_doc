MySQL: Access denied for user

What "Access denied for user '...'@'...' (using password: YES)" actually means, and how to fix it instead of guessing at passwords.

The error

You tried to connect — from the mysql CLI, a GUI client, or your application — and got:

ERROR 1045 (28000): Access denied for user 'app'@'localhost' (using password: YES)

Sometimes it's (using password: NO) instead — that variant means MySQL never even received a password, which is a different problem than a wrong one.

Why it happens

This error almost never means "you have a typo in your password" as often as people assume. MySQL user accounts are actually identified by a user@host pair, not just a username — 'app'@'localhost' and 'app'@'%' are two completely separate accounts as far as MySQL is concerned, and can have different passwords or not exist at all. Common causes, roughly in order of likelihood:

  • The account exists for a different host pattern than the one you're connecting from (e.g. it was created as 'app'@'%' but you're connecting from localhost, or vice versa).
  • The password really is wrong, or was reset and the app's config wasn't updated.
  • An authentication plugin mismatch — MySQL 8 defaults new users to caching_sha2_password, which many older client libraries (older PHP, some Node/Python drivers) can't speak.
  • (using password: NO) specifically: your client or connection string isn't sending a password at all, even though one is required.

Fix it

First, find out which user@host rows actually exist (run this as an account that already has access, e.g. root):

SELECT user, host FROM mysql.user WHERE user = 'app';

If the host column doesn't match where you're connecting from, either connect using a host pattern that does exist, or widen the account:

CREATE USER 'app'@'%' IDENTIFIED BY 'the-real-password';
GRANT ALL PRIVILEGES ON mydb.* TO 'app'@'%';
FLUSH PRIVILEGES;

If the account exists but you just need to reset the password:

ALTER USER 'app'@'localhost' IDENTIFIED BY 'a-new-password';

If the error only happens from certain client libraries and you suspect an auth plugin mismatch, switch that user back to the older, more broadly compatible plugin:

ALTER USER 'app'@'localhost' IDENTIFIED WITH mysql_native_password BY 'the-password';

The localhost vs 127.0.0.1 trap

On most installs, connecting to localhost makes the MySQL client use a local Unix socket file, not TCP — and that socket connection is authenticated against the 'user'@'localhost' row specifically. Connecting to 127.0.0.1 instead forces a real TCP connection, which is checked against 'user'@'127.0.0.1' or 'user'@'%'. If you've only ever granted one of the two, switching between localhost and 127.0.0.1 in your connection string can turn a working login into "access denied" with the exact same password — worth trying before you touch any permissions.
