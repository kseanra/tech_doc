.NET: Could not load file or assembly

What this error means, why "it works on my machine" is exactly the problem, and how to find the real cause instead of guessing.

The error

Your app throws this at startup or the first time a code path touches a particular library:

System.IO.FileNotFoundException: Could not load file or assembly 'Newtonsoft.Json,
Version=13.0.0.0, Culture=neutral, PublicKeyToken=30ad4fe6b2a6aeed' or one of its
dependencies. The system cannot find the file specified.

Why it happens

The .NET loader looked for an assembly with that exact name, version, and (for strong-named assemblies) public key token, and couldn't find a matching file anywhere it searched. That's a more specific failure than "the DLL is missing" — the DLL can be sitting right there in the output folder and this error still fires if its version doesn't match what the caller was compiled against. Typical causes:

  • A NuGet package restore didn't run (or ran against a different lock file), so the referenced version on disk doesn't match what the project was built against.
  • A transitive dependency isn't copied to the output directory — common when a project reference has CopyLocal/Private set to false, or a dependency is only resolved at the top-level app but a class library assumes it's already there.
  • Classic .NET Framework binding: two different parts of the app reference different versions of the same assembly, and there's no binding redirect telling the runtime which one to actually load.
  • An architecture or runtime mismatch — a native/mixed-mode assembly built for x64 loaded into an x86 process, or an assembly targeting a newer .NET runtime than what's installed on the machine running it.
  • The deployment machine is simply missing the corresponding shared runtime (a very common "works in CI, fails on the server" cause).

Fix it

Start clean — stale obj/bin folders holding an old, mismatched copy of an assembly is a frequent, boring cause:

dotnet clean
dotnet restore
dotnet build

Confirm the assembly actually exists next to your executable after building, and check its file version:

ls bin/Debug/net8.0/*.dll   # or the equivalent output folder for your TFM

On a deployment target, check which runtimes are actually installed — an app targeting net8.0 will fail to load its dependencies if only the .NET 6 runtime is present:

dotnet --list-runtimes

For classic .NET Framework projects hitting a version conflict between two references, add an explicit binding redirect to app.config / web.config so the runtime knows which version to prefer:

<dependentAssembly>
  <assemblyIdentity name="Newtonsoft.Json" publicKeyToken="30ad4fe6b2a6aeed" culture="neutral" />
  <bindingRedirect oldVersion="0.0.0.0-13.0.0.0" newVersion="13.0.0.0" />
</dependentAssembly>

Stop guessing: read the actual bind log

If the cause still isn't obvious, stop guessing and turn on assembly binding logging with the Fusion Log Viewer (fuslogvw.exe, ships with Visual Studio / the Windows SDK) or the COMPLUS_ETWEnabled/MDA equivalents on newer runtimes. It logs exactly which paths the loader probed for the failing assembly and why each one was rejected — which turns "could not load file or assembly" from a guessing game into a five-second read.
