Redis: connection refused

What "Error: connect ECONNREFUSED 127.0.0.1:6379" means, and why it often has nothing to do with Redis actually being down.

The error

Your app (or redis-cli) tries to connect and gets refused outright, not a timeout:

Error: connect ECONNREFUSED 127.0.0.1:6379

Or from the CLI directly:

Could not connect to Redis at 127.0.0.1:6379: Connection refused

A "refused" connection means something answered at that address and actively said no — which is a different, more specific situation than a hang, and it usually points at one of a handful of causes.

Why it happens

  • Redis isn't running at all — the most common cause, and the first thing to rule out.
  • Redis is running, but listening on a different port or a different bind address than your app is configured to use.
  • redis.conf has bind 127.0.0.1 (the default), so nothing outside the same machine can reach it — fine for a local dev box, a frequent surprise on a server or VM.
  • You're running Redis inside Docker and your app isn't — 127.0.0.1 inside a container refers to the container itself, not your host machine, so an app on the host trying to reach a containerized Redis via 127.0.0.1 will always be refused regardless of port-mapping mistakes.
  • The reverse: your app is also in Docker, in a different container or network, and is trying 127.0.0.1 instead of the Redis container's service name.

Fix it

First, confirm Redis is actually up and reachable at all:

redis-cli ping
# expect: PONG

If that fails, check whether the process is running, then start it:

# systemd hosts
systemctl status redis
systemctl start redis

# plain background process
redis-server --daemonize yes

If Redis responds to redis-cli ping locally but your app still can't connect, the two aren't talking to the same host/port — double-check your app's actual connection string or environment variable, not just what you assume it is.

If Redis runs in Docker and your app runs on the host (or in a different container), 127.0.0.1 is very likely the whole problem. On the same Docker Compose network, use the service name instead of an IP:

redis:
  image: redis:7
  ports:
    - "6379:6379"

app:
  environment:
    - REDIS_HOST=redis   # not 127.0.0.1 or localhost

From a non-Docker host process reaching into Docker Desktop on macOS/Windows, use host.docker.internal the other direction if your app is the one in the container and Redis is on the host.

If you need to allow connections from another real machine (not just container-to-container), edit redis.conf:

bind 0.0.0.0
protected-mode no   # only if you also set a requirepass — never expose Redis with neither

Isolate app bugs from server-down issues

Before changing any application code, run redis-cli -h <host> -p <port> ping using the exact host and port your app is configured with. If that succeeds, the problem is in your app's configuration, not Redis itself — if it also fails, you've confirmed the server/network side is the real issue and can stop debugging application code entirely.
