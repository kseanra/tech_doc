npm: ERESOLVE could not resolve

Why npm suddenly refuses to install a package it used to install fine, and how to fix the actual conflict instead of just forcing past it.

The error

npm install fails partway through with something like:

npm ERR! code ERESOLVE
npm ERR! ERESOLVE unable to resolve dependency tree
npm ERR!
npm ERR! While resolving: my-app@1.0.0
npm ERR! Found: react@16.14.0
npm ERR! node_modules/react
npm ERR!   react@"^16.14.0" from the root project
npm ERR!
npm ERR! Could not resolve dependency:
npm ERR! peer react@"^18.0.0" from some-library@3.2.0

Why it happens

A "peer dependency" is a package that says "I need you, the app installing me, to also have this other package at this version" — some-library above is saying it needs React 18 to work correctly, but your project has React 16 installed. Up through npm 6, npm installed packages anyway and just printed a warning if peer dependencies didn't match, leaving it to you to notice. Starting with npm 7, npm treats an unmet peer dependency as a hard error by default and refuses to install until the conflict is resolved — which is more correct, but breaks a lot of installs that used to "work" while silently running mismatched versions underneath.

Fix it properly

The real fix is to make the versions actually compatible: either upgrade the dependency that's out of date (here, React itself) to a version that satisfies the peer requirement, or find a version of the library requiring the peer dependency that supports your current version. Check what's actually available:

npm info some-library versions
npm outdated

Upgrading the root dependency is usually the right move if your project can tolerate it — read the target package's changelog for breaking changes first.

The shortcut, and when it's actually fine

If you've confirmed the mismatch doesn't matter in practice (common with libraries that declare an overly strict peer range but work fine across nearby versions), you can tell npm to fall back to the old, warning-only behavior:

npm install --legacy-peer-deps

This installs mismatched peers anyway rather than failing. Avoid npm install --force for this specific error — it bypasses the check entirely rather than falling back to a sane resolution strategy, and can silently produce a broken node_modules tree. Whichever way you resolve it, commit the resulting package-lock.json so the same resolution is reproduced for everyone on the team and in CI.
