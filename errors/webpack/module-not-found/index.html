Webpack/Vite: Module not found — Can't resolve

The bundler can't locate a file or package you imported. Almost always one of four specific causes.

The error

Running a dev server or build fails with something like:

ERROR in ./src/App.js
Module not found: Error: Can't resolve './components/Header' in '/project/src'

(Vite's phrasing is similar: Failed to resolve import "./components/Header" from "src/App.js".)

Why it happens, and how to fix each cause

1. A typo or wrong relative path. By far the most common cause — count the ../ segments carefully, and remember the path is relative to the importing file's own directory, not the project root. Open the target file directly at the path you typed to confirm it actually exists there.

2. Case mismatch that only fails on CI or Linux. macOS and Windows filesystems are case-insensitive by default, so import Header from './components/header' can work fine on your laptop while pointing at a file actually named Header.jsx, and then fail the moment it runs on a case-sensitive Linux CI runner or production server. This is one of the most common "works on my machine" bugs in frontend tooling specifically because local development usually hides it completely.

3. A missing or unconfigured file extension. If the actual file is Header.tsx but your bundler's resolve.extensions config doesn't include .tsx (common after adding TypeScript to a plain JS project's existing webpack config), an extension-less import silently fails to resolve even though the file is right there. Check the config:

// webpack.config.js
resolve: {
  extensions: ['.js', '.jsx', '.ts', '.tsx']
}

4. A path alias that's only configured on one side. An import like import Header from '@/components/Header' needs the @ alias defined in the bundler's own config (webpack's resolve.alias, Vite's resolve.alias) — and, separately, in tsconfig.json's paths if you're using TypeScript, since that file only affects type-checking, not how the bundler actually resolves the import at build time. Defining the alias in one but not the other produces exactly this error (or the inverse: TypeScript is happy, but the bundler can't find the file at runtime).

A quick way to narrow it down

Confirm the file genuinely exists exactly where you think, from the shell, rather than trusting your editor's file tree (which can cache a stale view after a rename):

ls -la src/components/

If the file is there and the casing matches exactly, move on to checking extensions and aliases; if it's a package from node_modules rather than your own code failing to resolve, that's a different problem — re-check the package name for typos and confirm it's actually listed in package.json's dependencies.
