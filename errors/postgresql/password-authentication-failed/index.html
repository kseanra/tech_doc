PostgreSQL: password authentication failed for user

Why this shows up even when you're sure the password is right, and how PostgreSQL actually decides which auth method to use.

The error

Connecting with psql, a client library, or an app fails with:

psql: error: connection to server at "localhost", port 5432 failed:
FATAL:  password authentication failed for user "postgres"

Why it happens

Unlike some databases, PostgreSQL doesn't use one universal auth method — it decides how to authenticate a connection attempt by matching it (by user, database, and connection source) against rules in a file called pg_hba.conf, read top to bottom, first match wins. The two methods people mix up most:

  • peer — trusts the operating system's own user account instead of a password, but only works for local socket connections where your OS username matches the Postgres role name.
  • md5 / scram-sha-256 — an actual password check, used for TCP connections (host entries, including 127.0.0.1 and remote hosts).

The password-authentication-failed error specifically means a rule requiring a password matched your connection, and the password you supplied didn't match what's stored — which can mean the password really is wrong, but just as often means the password was never set at all, or you're hitting a different auth rule than you expect (e.g. connecting over TCP to 127.0.0.1 when you meant to use the local peer-authenticated socket).

Fix it

Confirm which rule is actually matching your connection by reading pg_hba.conf (location varies by OS/install — SHOW hba_file; from an already-connected session will tell you exactly where):

sudo cat /etc/postgresql/*/main/pg_hba.conf | grep -v '^#'

If the role's password was never actually set (common right after a fresh install, where some distros create the postgres role with no password at all), set one from a session authenticated another way — typically peer, run as the matching OS user:

sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'newpassword';"

If you specifically want to connect locally without typing a password every time during development (never do this in production), you can change the relevant pg_hba.conf line's method to trust and reload:

sudo systemctl reload postgresql

The Docker version of this error

Running Postgres in a container, the equivalent trap is starting the container once without POSTGRES_PASSWORD set — the password is only initialized on the first startup with an empty data directory, so setting the environment variable on a container whose volume already has data does nothing. If you set the password after the fact, either connect and run ALTER USER as above, or wipe the data volume and let it reinitialize with the variable set correctly.
