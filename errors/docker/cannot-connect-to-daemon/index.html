Docker: cannot connect to the Docker daemon

What "Is the docker daemon running?" actually means, and the three real causes behind it.

The error

Any docker command — even docker ps — fails with:

Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the
docker daemon running?

On Windows it usually names a named pipe instead of a unix socket, but the meaning is identical.

Why it happens

The docker command you type is only a client — it doesn't run containers itself. It talks to a background service, the Docker daemon (dockerd), over a local socket, and every single Docker command needs that connection to succeed. This error means the client couldn't reach the daemon at all, for one of three reasons:

  • The daemon isn't running. On macOS and Windows that means Docker Desktop itself isn't started; on Linux it means the docker service isn't active.
  • Permission denied on the socket (Linux only) — the socket file exists and the daemon is running, but your user isn't in the group allowed to talk to it. This shows up as a slightly different message mentioning "permission denied," but leads here for the same underlying reason.
  • Wrong target — a DOCKER_HOST environment variable is pointing the client at a socket, host, or context that isn't valid (common right after switching between Docker Desktop and a remote/VM-based setup).

Fix it

On macOS or Windows, first confirm Docker Desktop is actually open and fully started (its icon typically shows a status indicator while starting up) — most instances of this error are just the daemon not being up yet.

On Linux, check whether the service is running and start it if not:

sudo systemctl status docker
sudo systemctl start docker

If the daemon is running but you're still blocked, it's almost always the permission case — add your user to the docker group so you don't need sudo for every command, then start a new shell session (group membership only applies to new logins):

sudo usermod -aG docker $USER
newgrp docker

If you've used Docker contexts or remote Docker setups before, check which one is currently selected — it's easy to be pointed at a context whose host is no longer reachable:

docker context ls
docker context use default

Also check for a stray DOCKER_HOST in your shell profile overriding the client's target: echo $DOCKER_HOST. If it's set and shouldn't be, unset it or fix the value.
