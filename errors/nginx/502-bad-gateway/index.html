Nginx: 502 Bad Gateway

What nginx is actually telling you, and where to look instead of restarting things at random.

The error

A visitor (or you) gets nginx's own error page:

502 Bad Gateway
nginx

Why it happens

Nginx is usually sitting in front of your app as a reverse proxy, not serving the app itself. A 502 means nginx successfully received the request and tried to forward it to the upstream app — but got back an invalid response, or no response at all, from that upstream. Common causes:

  • The upstream app isn't running, crashed, or is mid-restart (very common right after a deploy).
  • Nginx's proxy_pass points at the wrong port or the wrong Unix socket path for what's actually running.
  • A Unix socket file exists, but its permissions don't allow nginx's worker process (often running as www-data or nginx) to connect to it.
  • The upstream took too long to respond and the connection was closed, or it closed the connection itself mid-response.

Fix it

Read nginx's error log before touching anything — it names the exact upstream and the exact reason, instead of leaving you to guess:

tail -f /var/log/nginx/error.log

Typical lines look like connect() failed (111: Connection refused) (nothing listening where nginx expected) or connect() to unix:/run/app.sock failed (13: Permission denied) (a socket permissions problem specifically).

Confirm the app itself is actually up:

systemctl status myapp

If it's a socket permissions issue, check the socket file's owner and mode, and that nginx's user is in the right group to reach it. If it's a timeout under load rather than a hard failure, you can raise the ceiling in the relevant server or location block:

proxy_connect_timeout 10s;
proxy_read_timeout    30s;

Treat a timeout increase as a stopgap, not a fix — if the upstream is genuinely too slow under normal load, the real problem is on the app side.

502 vs 504 — they're not the same problem

504 Gateway Timeout means nginx never got a response from the upstream at all within the allowed time — the connection was made, but nothing came back in time. 502 means either the connection itself failed (refused, reset) or the upstream sent back something nginx couldn't parse as a valid HTTP response. Raising proxy_read_timeout can fix a 504; it does nothing for a 502 caused by the upstream being down or misconfigured, so check the error log first rather than assuming it's a timing issue.
